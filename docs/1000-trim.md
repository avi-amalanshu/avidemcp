# trim

> Keep one range of a clip; exact mode re-encodes frame-accurately, copy mode is lossless but starts on an I-frame.

Tree: `1000` < `100` Ranges < `10` One edit per call < `1` Edit < root ([AGENTS.md](../AGENTS.md))

## Call

```
trim {"input": "clip.mov", "start": 2.5, "end": 9}
trim {"input": "long.mov", "start": 312, "end": 655, "mode": "copy"}
-> {"output": "long.trim.mov", "kept": [[311.0, 655.0]], ...}
```

| Argument | Default | Meaning |
|---|---|---|
| `start` | 0 | first second kept |
| `end` | end of clip | first second not kept |
| `mode` | `"exact"` | `exact`: frame-accurate re-encode to H.264 MP4; `copy`: no re-encode, input's container |
| `snap` | `true` | copy mode only; see below |
| `crf` | 18 | exact mode only |
| `output` | `<stem>.trim.mp4` (exact) or `<stem>.trim.<input ext>` (copy) | |

## Modes

- `exact` keeps exactly the frames in `[start, end)` and the matching audio, and encodes once.
- `copy` (Avidemux's "Copy" output) takes seconds even on long files and loses no quality. Video
  can only start cleanly on an I-frame, so with `snap: true` the start moves back to the I-frame at
  or before `start`. The result begins early; `kept` gives the source range that survived.
- `copy` with `snap: false` starts exactly at `start`, on frames whose reference picture is gone.
  Depending on the decoder, the start shows grey, garbage or nothing until the next I-frame.

## When to use which

- `exact` whenever the start point matters.
- `copy` to shorten a long file quickly when `probe` shows I-frames close to where you want to
  start. For a frame-exact start on a long file, copy-trim with a margin, then exact-trim the short
  result: only the short part is re-encoded.
- On a file made by `prepare`, I-frames are sparse, so copy mode can keep far more than you asked.
- For several edits to one file, one `render` with `trim` and `cut` ops encodes once instead of
  once per call.
